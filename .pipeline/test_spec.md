# Test Specification

> **WARNING — `.pipeline/surface.json` is stale.** The checked-in `surface.json` is the
> untouched `template-enterprise` scaffold contract. It advertises only `GET /health`,
> `GET /trpc/users.findAll`, `GET /trpc/users.findById` and the demo `app-home` component —
> none of which are the StockRoom surface. The authoritative API surface used below is
> derived from the approved spec plus the route table in `.pipeline/tasks.md`.
> `requirements/spec.md` does not exist in this worktree; the `<spec>` input was used directly.
>
> Consequences for testing:
> 1. The three stale `surface.json` routes are still covered below — as **retirement**
>    assertions (the tRPC demo surface must be gone or inert, and health must live at the
>    prefixed path). If the implementer chooses to keep the tRPC module mounted, those cases
>    flip from "gone" to "still 200" — see API-001…API-004.
> 2. `surface.json` MUST be regenerated by the implementer with the real routes,
>    components and `data-testid`s before this spec's coverage numbers are meaningful.
> 3. `.colossus-acceptance.json` currently has `expect_text: []` and reject signatures
>    `home-title">Users<`, `Loading...`, `Failed to load users.` — the smoke journey
>    (UI-001) encodes those, and `expect_text` should be set to `["StockRoom"]`.
>
> **Role vocabulary.** The spec says `clerk`/`manager`; the platform contract
> (`colossus.stack.json`) mints `ADMIN`/`MANAGER`/`USER`. Per `tasks.md`, tests use
> `clerk → USER` and `manager → MANAGER or ADMIN`, with ADMIN a strict superset of MANAGER
> and MANAGER a strict superset of USER. Credentials come from `COLOSSUS_ACCOUNTS_JSON`,
> not the hardcoded `manager@demo` / `clerk@demo` in the spec.

## Coverage summary
- Total cases: 357 (214 API, 123 UI/journey, 20 data-integrity)
- API endpoints covered: 23 / 3 in `surface.json` — 3/3 of the stale scaffold routes (as retirement checks) plus 20 real StockRoom routes derived from the spec + `tasks.md`
- User journeys covered: 25 (23 browser flows + 1 guard/query-param unit suite + 1 build/static-contract check)

**Case ID scheme:** `API-nnn` (HTTP-level, supertest), `UI-nnn` (browser/journey or Angular unit),
`DATA-nnn` (database invariant, asserted via Prisma after a mutation).

**Shared fixtures assumed by every API case**
- `tokenUser` — JWT for a `USER`-role platform account.
- `tokenManager` — JWT for a `MANAGER`-role platform account.
- `tokenAdmin` — JWT for the always-present `ADMIN` platform account.
- No `Authorization` header = anonymous.
- Each spec file seeds its own items/locations with unique SKUs (e.g. `TEST-<file>-001`) so
  files can run against a shared `DATABASE_URL` without cross-contamination, and cleans up
  in `afterAll`. Absolute row counts are never asserted — only deltas.

### `POST /api/auth/signup`
- **Happy path**:
  - `API-013` — `{ email: 'newuser+<rand>@test.local', password: 'Passw0rd!23' }` → **201** with

    the body.

    `USER` (not ADMIN). Decoding the JWT payload yields `{ sub, email, role: 'USER' }`.
  - `API-015` — the returned `accessToken` immediately authenticates `GET /api/auth/me`.
- **Validation failures**:
  - `API-016` — missing `email` → **400** with a `class-validator` message naming `email`.
  - `API-017` — missing `password` → **400** naming `password`.
  - `API-018` — `email: 'not-an-email'` → **400**.
  - `API-019` — `password: '123'` (below minimum length) → **400**.
  - `API-020` — extra unknown property `{ role: 'ADMIN' }` in the body is stripped by
    `whitelist: true`: the request either 400s or succeeds with `role === 'USER'` —
    privilege escalation via the signup body is impossible.
  - `API-021` — duplicate email (signup twice with the same address) → **422** with a
    field-level error identifying `email`, **not** 409 and not 500.
- **Auth failures**: n/a — route is `@Public()`; `API-022` asserts an anonymous request succeeds.
- **Idempotency / edge cases**:
  - `API-023` — after the duplicate-email 422 (API-021), `User` count is unchanged (see DATA-002).
  - `API-024` — email is matched case-insensitively or normalised: signing up
    `Dup@test.local` after `dup@test.local` returns 422 (or, if the implementation is
    case-sensitive by design, the behaviour is documented and consistent with login).

### `GET /api/items`
- **Happy path**:
  - `API-048` — `tokenUser` → **200** with `{ data: Item[], total, page, pageSize }` (or the
    implementation's `Paginated<T>` shape, asserted consistently across all list endpoints).
  - `API-049` — each row carries `id, sku, name, unit, reorderAt` **and** an aggregated
    `totalQty: number`.
  - `API-050` — `totalQty` equals the sum of that item's `StockLevel.qty` across all locations;
    an item with no `StockLevel` rows reports `totalQty: 0`, not `null` and not omitted.
  - `API-051` — `tokenManager` and `tokenAdmin` get the same 200 (read is USER+).
  - `API-052` — `?q=SKU-00` filters to matching SKUs; `?q=<item name fragment>` matches on name.
    A `q` that matches nothing returns `{ data: [], total: 0 }` with **200**, not 404.
  - `API-053` — `?lowStock=true` returns only items where `totalQty <= reorderAt`; an item
    seeded with `reorderAt: 10, totalQty: 40` is absent, one with `reorderAt: 10, totalQty: 3`
    is present.
  - `API-054` — `?lowStock=false` (and omitting the param) returns the unfiltered set.
  - `API-055` — `?page=1&pageSize=2` returns exactly 2 rows; `?page=2&pageSize=2` returns a
    disjoint set (no id overlap with page 1) and the same `total`.
  - `API-056` — default `pageSize` is **25** when omitted (seed >25 items in the fixture, assert
    `data.length === 25`).
  - `API-057` — `?q=` and `?lowStock=true` combine (AND, not OR).
- **Validation failures**:
  - `API-058` — `?page=0` → **400** (or coerced to 1 — assert whichever, consistently; must not
    produce a negative SQL `OFFSET`).
  - `API-059` — `?page=abc` → **400**.
  - `API-060` — `?pageSize=-5` → **400**.
  - `API-061` — `?pageSize=100000` → **400** or clamped to the documented max; must not attempt
    to return the whole table.
  - `API-062` — `?lowStock=maybe` → **400** (boolean coercion is strict).
  - `API-063` — an unknown query param `?bogus=1` is stripped by `whitelist` and does not 500.
  - `API-064` — `?q=' OR 1=1--` returns 0 rows and 200 (Prisma parameterisation; no SQL injection).
- **Auth failures**:
  - `API-065` — anonymous → **401**. *(This is the spec's "unauthenticated API" scenario and the
    proof that `JwtAuthGuard` is registered as an `APP_GUARD`.)*
  - `API-066` — expired token → **401**.
- **Idempotency / edge cases**:
  - `API-067` — the endpoint is read-only: two identical calls return identical bodies and the
    `Item` row count is unchanged.

- **Idempotency / edge cases**:
  - `API-166` — **concurrency**: two simultaneous `OUT` requests (fired with `Promise.all`, no
    `await` between them) that would jointly overdraw a location holding 10 (each requesting 8):
    exactly **one** returns 201 and exactly **one** returns 422; the final balance is **2** and
    is never negative; exactly one `Movement` row exists for the pair.
  - `API-167` — the same concurrency scenario repeated 5× in a loop never produces a deadlock
    error (P2034 / "deadlock detected"), validating the deterministic `ORDER BY id`
    `SELECT … FOR UPDATE` lock ordering.
  - `API-168` — two concurrent `IN` movements of 10 each into the same fresh (item, location)
    pair both succeed and the balance is exactly **20** — no lost update, and the
    `@@unique([itemId, locationId])` constraint does not surface as a 500.
  - `API-169` — movements are immutable: `PATCH /api/movements/:id` and
    `DELETE /api/movements/:id` both return **404** (no such route exists).

### `GET /api/movements`
- **Happy path**:
  - `API-170` — `tokenManager` → **200** with a paginated list; each row includes `user.email`,
    `item.sku`, `item.name`, `type`, `qty`, both location names (`fromLoc`/`toLoc`, null-safe for
    IN/OUT) and `createdAt`. *(Spec scenario: the log lists user + item + type + qty + timestamp.)*
  - `API-171` — ordering is `createdAt desc` — after recording three movements in sequence, the
    most recent is `data[0]`.
  - `API-172` — `?itemId=<id>` returns only that item's movements; a second item's movements are
    absent. *(Spec scenario: item filter.)*
  - `API-173` — `?type=IN` returns only IN rows; `?type=TRANSFER` only transfers.
  - `API-174` — `?from=<today ISO date>` is **inclusive** — a movement created today is included.
  - `API-175` — `?to=<today ISO date>` is **end-of-day inclusive** — a movement created at
    23:00 today is included when `to` is today's date. *(Spec scenario: date-range filter.)*
  - `API-176` — `?from=<tomorrow>` returns `{ data: [], total: 0 }` with 200.
  - `API-177` — `?from=X&to=X` (single-day window) returns exactly that day's movements.
  - `API-178` — filters compose: `?itemId=A&type=OUT&from=…&to=…` ANDs all four.
  - `API-179` — `?page=2&pageSize=1` returns the second-newest row and is disjoint from page 1;
    `total` reflects the filtered count, not the table count.
  - `API-180` — default `pageSize` is **25**.
  - `API-181` — the seeded database returns a **non-empty** log on first load (seed writes
    movements rather than `StockLevel` rows directly).
- **Validation failures**:
  - `API-182` — `?type=BOGUS` → **400**.
  - `API-183` — `?from=not-a-date` → **400**.
  - `API-184` — `?from` after `?to` → **400** or an empty 200 result; asserted consistently, never 500.
  - `API-185` — `?itemId=not-a-uuid` → **400** or an empty 200 result, never 500.
  - `API-186` — `?page=0` / `?pageSize=-1` → **400**.
- **Auth failures**:
  - `API-187` — anonymous → **401**.
  - `API-188` — `tokenUser` (clerk tier) → **403** — the audit log is manager-only.
- **Idempotency / edge cases**:
  - `API-189` — read-only: calling it does not create movements; `total` is stable across two calls.

### `GET /api/reports/low-stock`
- **Happy path**:
  - `API-190` — `tokenManager` → **200** with rows shaped `{ item, totalQty, reorderAt, deficit }`.
  - `API-191` — an item with `reorderAt: 10` and **12** on hand, after an `OUT` of 5 (→ 7 on hand),
    **appears** in the report with `totalQty: 7`, `reorderAt: 10`, `deficit: 3`. *(Spec scenario.)*
  - `API-192` — an item with `reorderAt: 10` and **40** on hand is **absent**. *(Spec scenario.)*
  - `API-193` — boundary: `totalQty === reorderAt` (exactly 10 on hand, reorderAt 10) **is**
    included — the predicate is `<=`, not `<`; `deficit` is 0.
  - `API-194` — an item with **no** `StockLevel` rows at all counts as `totalQty: 0` and appears
    (left-join semantics), with `deficit === reorderAt`.
  - `API-195` — the total is summed **across all locations**: 4 units in Zone A + 3 in Zone B
    against `reorderAt: 10` yields one row with `totalQty: 7`, not two rows.
  - `API-196` — ordering is by `(totalQty - reorderAt)` ascending — the most-deficient item is first.
  - `API-197` — a freshly seeded database returns ≥2 rows (the seed guarantees ≥2 items at or
    below threshold so the report is non-empty on first load).
  - `API-198` — recording an `IN` that lifts an item above its threshold removes it from the
    report on the next call.
- **Validation failures**: n/a — the endpoint takes no parameters; `API-199` asserts an unknown
  query param `?foo=1` is ignored and returns 200.
- **Auth failures**:
  - `API-200` — anonymous → **401**.
  - `API-201` — `tokenUser` → **403**.
- **Idempotency / edge cases**:
  - `API-202` — two consecutive calls with no intervening mutation return identical bodies.

### `GET /api/admin/settings`
- **Happy path**:
  - `API-203` — `tokenAdmin` → **200** with one entry per provisioned service key
    (`postgresql`, `minio`), each `{ key, value: <masked>, configured: boolean }`.
  - `API-204` — values are **masked** — the raw `DATABASE_URL` / minio secret never appears in
    the response body.
  - `API-205` — a key whose value is absent **or** equal to `PLACEHOLDER_CONFIGURE_IN_SETTINGS`
    reports `configured: false`; a key with a real value reports `true`.
- **Validation failures**: n/a (no inputs).
- **Auth failures**:
  - `API-206` — anonymous → **401**.
  - `API-207` — `tokenUser` → **403**.
  - `API-208` — `tokenManager` → **403** — admin-only, proving MANAGER is *not* a superset of ADMIN.
- **Idempotency / edge cases**:
  - `API-209` — read-only: no `SystemSetting` rows are created by a GET.

### `PATCH /api/admin/settings`
- **Happy path**:
  - `API-210` — `tokenAdmin` with `{ minio_access_key: 'abc' }` → **200**; a follow-up GET reports
    that key `configured: true` with a masked value.
  - `API-211` — patching an existing key **upserts** (updates in place, no duplicate
    `SystemSetting` rows for the same `key`).
  - `API-212` — `resolveConfig` precedence: with the env var set to a real value, `resolveConfig`
    returns the env value even after a `SystemSetting` row is written; with the env var absent
    **or** equal to `PLACEHOLDER_CONFIGURE_IN_SETTINGS`, it falls back to the `SystemSetting`
    row; with neither, it returns `null` and the dependent endpoint surfaces **503**
    (`ServiceUnconfiguredError`), not 500.
- **Validation failures**:
  - `API-213` — a non-object / empty body → **400**; an unknown key is rejected (400) or ignored,
    asserted consistently and never written blindly.
- **Auth failures**:
  - `API-214` — anonymous → **401**; `tokenUser` → **403**; `tokenManager` → **403**.

## Data integrity tests

Asserted directly against Postgres via Prisma immediately after the referenced API call.

- `DATA-001` — after a duplicate-SKU `POST /api/items` → 422, `Item.count()` is **unchanged**
  from its pre-request value.
- `DATA-002` — after a duplicate-email signup → 422, `User.count()` is unchanged.
- `DATA-003` — after a duplicate `(name, zone)` `POST /api/locations` → 422, `Location.count()`
  is unchanged.
- `DATA-004` — **no negative balances, ever**: after every movement case in this spec,
  `SELECT count(*) FROM "StockLevel" WHERE qty < 0` is **0**. Asserted as a global `afterEach`
  invariant across the whole movement suite, not just the insufficient-stock case.
- `DATA-005` — **conservation under TRANSFER**: `SUM(StockLevel.qty)` for a given `itemId` is
  identical before and after any `TRANSFER`.
- `DATA-006` — **balance reconciles to the ledger**: for every (item, location) pair,
  `StockLevel.qty` equals `SUM(IN.qty to loc) + SUM(TRANSFER.qty to loc) - SUM(OUT.qty from loc)
  - SUM(TRANSFER.qty from loc)` computed from the `Movement` table. The `StockLevel` cache is
  always derivable from the immutable audit log.
- `DATA-007` — **atomic rollback**: after a 422 `Insufficient stock`, the affected `StockLevel`
  rows are byte-identical to their pre-request values **and** no `Movement` row was written for
  that attempt (the count of movements for that item is unchanged).
- `DATA-008` — after a 409 on `DELETE /api/items/:id`, the `Item`, its `StockLevel` rows and all
  referencing `Movement` rows still exist.
- `DATA-009` — after a 409 on `DELETE /api/locations/:id`, the `Location` and its non-zero
  `StockLevel` rows still exist; no quantity was silently orphaned.
- `DATA-010` — **no orphans**: every `StockLevel.itemId` resolves to an `Item`, every
  `StockLevel.locationId` resolves to a `Location`, and every non-null `Movement.fromLocId` /
  `toLocId` / `itemId` / `userId` resolves to an existing row. Run as a suite-wide teardown check.
- `DATA-011` — **uniqueness constraints hold**: no two `StockLevel` rows share
  `(itemId, locationId)`; no two `Item` rows share `sku`; no two `Location` rows share
  `(name, zone)`; no two `User` rows share `email` — asserted by query, so a constraint dropped
  from a migration is caught.
- `DATA-012` — **SKU normalisation is total**: `SELECT count(*) FROM "Item" WHERE sku <> upper(btrim(sku))`
  is 0 after any create/update path.
- `DATA-013` — **movement attribution**: every `Movement.userId` equals the `sub` of the JWT that
  created it; seeded movements are attributed to the platform ADMIN account.
- `DATA-014` — **movements are append-only**: after the full suite, no `Movement` row's `id`
  disappears and none has a mutated `qty`/`type`/`createdAt` (snapshot the ledger at two points
  and diff — the earlier snapshot must be a prefix of the later one).
- `DATA-015` — **concurrency safety**: after the concurrent double-`OUT` case (API-166), exactly
  one `Movement` row exists for the pair and `StockLevel.qty` equals the single applied delta —
  no lost update, no double-spend.
- `DATA-016` — **seed idempotency**: running the seed twice produces the same
  `Item`/`Location`/`User` counts and does **not** duplicate opening-stock movements or double
  the balances. The platform `COLOSSUS_ACCOUNTS_JSON` → `ColossusAccount` + `User`
  materialisation still succeeds on the second run.
- `DATA-017` — **seed guarantees a useful demo**: after seeding, `Movement.count() > 0` and at
  least **2** items satisfy `SUM(StockLevel.qty) <= reorderAt`, so the audit log and low-stock
  report are non-empty on first load.
- `DATA-018` — **passwords are hashed**: no `User.passwordHash` equals a plaintext password, every
  hash matches the bcrypt prefix (`$2a$`/`$2b$`/`$2y$`), and no endpoint response body in the
  entire suite ever contains the substring `passwordHash`.
- `DATA-019` — **required indexes exist**: `StockLevel` has a unique index on `(itemId, locationId)`
  and an index on `locationId`; `Movement` has indexes on `(itemId, createdAt)` and `createdAt`
  (verified via `pg_indexes`) — the migration, not just the schema file, carries them.
- `DATA-020` — **schema/migration parity**: `npx prisma migrate deploy` against a fresh database
  followed by `prisma migrate diff` reports **no drift** between `schema.prisma` and the applied
  migrations.

## Out of scope

- **Refresh tokens / session revocation.** The spec explicitly ships a single 12h access token
  with no refresh flow; `API-040` documents that logout does not invalidate the JWT server-side
  rather than testing a revocation mechanism that does not exist.
- **Password reset, email verification, account lockout, rate limiting.** The spec is silent on
  all of them; no endpoints exist to test.
- **Hardcoded demo credentials (`manager@demo` / `clerk@demo` / `Demo1234!`).** `tasks.md`
  resolves the conflict in favour of platform-minted `COLOSSUS_ACCOUNTS_JSON` accounts, so no
  test asserts those literals. If the README is required to document fixed demo logins, that is
  an open question for the spec owner, not a test gap.
- **minio / object storage behaviour.** Provisioned as a backing service but the spec describes no
  upload feature. Only its presence in admin settings and its `resolveConfig` fallback are tested
  (API-203…API-212); no upload/download path exists.
- **tRPC surface behaviour.** The spec mandates REST. The stale `/trpc/users.*` routes are tested
  only for retirement or inertness (API-003, API-004), not for correctness.
- **`GET /api/docs` (Swagger) content.** Kept mounted only as the stack's backend probe path;
  its contents are not asserted beyond the probe returning a non-5xx response.
- **Movement update/delete semantics.** Movements are immutable by design; `API-169` asserts the
  routes are absent rather than testing edit behaviour.
- **Multi-tenancy, soft deletes, audit of non-movement entities.** Item and location
  create/update/delete are **not** written to the `Movement` audit log — the spec scopes the log
  to stock movements only.
- **Cross-item transfers, partial/backordered fulfilment, reservations, units of measure
  conversion.** Not in the spec's data model.
- **Docker / Kubernetes runtime verification.** Docker and psql are not installed on the build
  machine (a stated spec risk), so container startup, `prisma migrate deploy` in the entrypoint,
  readiness probes and the nginx→backend proxy are verified only statically (UI-122, UI-123) plus
  in the Colossus pipeline's own deploy gate. Backend tests must run against any reachable
  `DATABASE_URL`.
- **Colossus deploy-pipeline layout assumptions.** Whether the pipeline expects the
  `backend/` + `frontend/` + `k8s/` layout and these image names is undiscoverable from this repo;
  a mismatch is a deploy-time finding, not a test case.
- **Accessibility, i18n, responsive breakpoints, visual regression, browser matrix.** The spec
  defines no acceptance criteria for any of them.
- **Performance and load beyond the concurrency correctness cases.** API-166…API-168 test
  correctness under contention; throughput/latency targets are unspecified.
- **`.pipeline/surface.json` regeneration itself.** Flagged as required implementer work in the
  warning above; this spec covers the routes it *should* contain, not the act of regenerating it.
